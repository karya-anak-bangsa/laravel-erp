Disk rusak, server diretas, atau salah menjalankan DELETE tanpa WHERE: kehilangan data jarang datang dengan pemberitahuan. Bagi toko online atau sistem kasir UMKM, hilangnya data transaksi seminggu saja bisa berarti hilangnya catatan penjualan sekaligus kepercayaan pelanggan.

Kabar baiknya, backup otomatis MySQL bisa disiapkan dalam satu sore. Artikel ini membahas cara membuat dump yang konsisten dengan mysqldump, menyimpan kredensial dengan aman, menjadwalkannya di Linux maupun Windows, mengatur masa simpan, menyimpan salinan di luar server, hingga menguji pemulihan.

Membuat Dump yang Konsisten dengan mysqldump

mysqldump menghasilkan berkas berisi perintah SQL yang bisa dijalankan ulang untuk membangun kembali database. Opsi terpentingnya adalah --single-transaction. Opsi ini memulai transaksi sebelum membaca data, sehingga hasil dump mencerminkan kondisi database pada satu titik waktu tanpa mengunci tabel dan tanpa menghentikan aplikasi.

Ada dua catatan penting. Konsistensi itu hanya berlaku untuk tabel InnoDB, dan selama dump berjalan jangan jalankan perintah seperti ALTER TABLE atau TRUNCATE TABLE pada tabel yang sedang di-backup, karena hasilnya bisa keliru atau gagal.

Berikut contoh perintah lengkap di Linux, sekaligus dikompresi dengan gzip agar ukuran berkasnya jauh lebih kecil:

mysqldump --defaults-extra-file=/etc/mysql/backup.cnf --single-transaction --routines --events toko_db | gzip > /var/backups/mysql/toko_db-$(date +%F).sql.gz

Opsi --routines dan --events ditambahkan karena stored procedure, function, dan event tidak ikut secara bawaan, sedangkan trigger sudah ikut otomatis. Bagian $(date +%F) menghasilkan tanggal seperti 2026-07-02, sehingga setiap berkas punya nama unik per hari.

Jangan Tulis Password di Baris Perintah

Menulis password langsung di perintah, misalnya -pRahasia123, memang praktis tetapi berisiko. Di beberapa sistem, perintah yang sedang berjalan bisa dilihat pengguna lain lewat program seperti ps, dan perintah itu juga bisa tersimpan di riwayat shell.

Simpan kredensial di option file. Buat berkas /etc/mysql/backup.cnf berisi bagian [client] dengan baris user dan password, lalu batasi aksesnya dengan chmod 600 /etc/mysql/backup.cnf agar hanya pemiliknya yang bisa membaca. Opsi --defaults-extra-file harus ditulis sebelum opsi lain, seperti pada contoh di atas.

Gunakan juga user MySQL khusus backup, bukan root. Setelah membuatnya dengan CREATE USER, beri hanya hak yang dibutuhkan mysqldump, tanpa hak menulis: GRANT SELECT, SHOW VIEW, TRIGGER, EVENT, PROCESS ON *.* TO 'pencadang'@'localhost';. Dengan begitu, berkas kredensial yang bocor tidak bisa dipakai untuk mengubah atau menghapus isi tabel.

Menjadwalkan Backup Otomatis

Linux dengan cron

Simpan perintah mysqldump tadi di skrip bash, misalnya /usr/local/bin/backup-mysql.sh, dan awali isinya dengan set -o pipefail. Tanpa opsi itu, kegagalan mysqldump bisa tertutupi karena gzip tetap selesai dengan sukses, meninggalkan berkas yang tampak normal padahal kosong atau terpotong.

Jadwalkan lewat crontab -e dengan baris 30 1 * * * /usr/local/bin/backup-mysql.sh agar backup berjalan setiap hari pukul 01.30. Menaruh perintah di skrip juga menghindari jebakan crontab: tanda % di baris crontab diperlakukan sebagai baris baru, sehingga $(date +%F) yang ditulis langsung di sana tidak berjalan sesuai harapan.

Windows dengan Task Scheduler

Di Windows, simpan perintahnya dalam berkas skrip, misalnya C:\backup\backup-mysql.bat, dan tulis path lengkap ke mysqldump.exe karena tugas terjadwal belum tentu memakai PATH yang sama dengan terminal Anda. Gunakan opsi --result-file untuk menulis hasil dump, bukan tanda >. Dokumentasi MySQL mengingatkan bahwa pengalihan output di PowerShell menghasilkan berkas UTF-16 yang tidak bisa dipulihkan dengan benar.

Daftarkan skripnya dengan schtasks /create /tn "Backup MySQL" /tr C:\backup\backup-mysql.bat /sc daily /st 01:30, atau lewat menu Create Basic Task di aplikasi Task Scheduler. Pada properti tugas, pilih Run whether user is logged on or not agar backup tetap berjalan walau tidak ada yang login.

Atur Masa Simpan dan Simpan Salinan di Luar Server

Backup harian yang tidak pernah dihapus lama-lama akan memenuhi disk. Tentukan masa simpan, misalnya 14 hari, lalu tambahkan baris berikut di akhir skrip Linux: find /var/backups/mysql -name "*.sql.gz" -mtime +14 -delete. Pola berjenjang juga umum dipakai, misalnya backup harian disimpan dua minggu, mingguan dua bulan, dan bulanan setahun.

Yang tidak kalah penting, backup yang hanya tersimpan di server yang sama akan ikut hilang bila server itu rusak atau diretas. Terapkan aturan 3-2-1 berikut:

  • Tiga salinan data, yaitu data asli ditambah dua cadangan.

  • Dua jenis media atau tempat penyimpanan yang berbeda, misalnya disk server dan object storage.

  • Satu salinan di luar lokasi utama, misalnya di layanan cloud atau server di kota lain.

Alat seperti rclone atau rsync bisa menyalin berkas backup ke lokasi lain secara otomatis setelah dump selesai. Bila database berisi data pribadi pelanggan, enkripsi dulu berkasnya sebelum diunggah.

Uji Pemulihan secara Berkala

Backup yang belum pernah dicoba dipulihkan belum layak disebut backup. Jadwalkan uji pemulihan, misalnya sebulan sekali, ke database terpisah dengan langkah berikut:

  1. Buat database kosong khusus uji, misalnya toko_db_uji.

  2. Pulihkan berkas terbaru dengan gunzip < toko_db-2026-07-01.sql.gz | mysql -u root -p toko_db_uji.

  3. Bandingkan jumlah baris tabel penting, misalnya pesanan dan pelanggan, dengan database produksi.

  4. Catat lama proses pemulihan agar Anda tahu perkiraan waktu henti bila bencana benar-benar terjadi.

Untuk Database Besar, Lirik MySQL Shell

mysqldump nyaman untuk database kecil hingga menengah. Namun dokumentasi resminya sendiri menyebut alat ini tidak dirancang untuk backup data berukuran besar, karena pemulihannya bisa sangat lambat ketika setiap perintah SQL harus dijalankan ulang.

Alternatifnya adalah utilitas dump di MySQL Shell. Perintah seperti util.dumpSchemas(["toko_db"], "/var/backups/mysql/toko_db-dump") menjalankan dump paralel dengan beberapa thread, mengompresi berkas secara bawaan, dan menampilkan progres. Pemulihannya memakai util.loadDump(). Untuk data yang jauh lebih besar lagi, pertimbangkan backup fisik yang menyalin berkas data secara langsung.

Mulai Hari Ini

Backup otomatis adalah kebiasaan kecil yang nilainya baru terasa saat musibah datang. Mulailah dari yang sederhana: satu skrip mysqldump dengan --single-transaction, kredensial di option file, jadwal harian, masa simpan yang jelas, dan setidaknya satu salinan di luar server.

Setelah itu, jadikan uji pemulihan sebagai agenda rutin, bukan kegiatan saat panik. Rincian setiap opsi bisa Anda periksa di dokumentasi mysqldump.
