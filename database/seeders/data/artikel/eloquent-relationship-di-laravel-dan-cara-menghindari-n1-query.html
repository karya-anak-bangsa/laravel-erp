Halaman daftar artikel yang dulu terbuka dalam sekejap tiba-tiba terasa berat setelah datanya mencapai ratusan baris. Sering kali penyebabnya bukan server yang kurang kuat, melainkan puluhan hingga ratusan query kecil yang dijalankan diam-diam oleh Eloquent.

Artikel ini mengulas empat relasi Eloquent yang paling sering dipakai, lalu membedah masalah N+1 query: dari mana asalnya, cara memperbaikinya dengan eager loading, dan cara mendeteksinya sebelum dirasakan pengguna.

Empat Relasi yang Paling Sering Dipakai

Relasi di Eloquent ditulis sebagai method di dalam model. Laravel menebak nama kolom dari konvensi, jadi tabel posts cukup punya kolom user_id agar terhubung ke tabel users tanpa konfigurasi tambahan.

  • hasOne, untuk satu baris yang punya tepat satu pasangan, misalnya user dengan profilnya. Di model User: return $this->hasOne(Profile::class);

  • hasMany, untuk satu baris yang punya banyak pasangan, misalnya satu penulis dengan banyak artikel: return $this->hasMany(Post::class);

  • belongsTo, kebalikan dari keduanya, dipasang di model yang menyimpan foreign key. Di model Post: return $this->belongsTo(User::class);

  • belongsToMany, untuk relasi banyak ke banyak lewat tabel perantara, misalnya artikel dan tag. Laravel mengharapkan tabel post_tag, yaitu gabungan nama kedua model menurut urutan abjad: return $this->belongsToMany(Tag::class);

Bila tabel tidak mengikuti konvensi, misalnya kolom penulis bernama author_id, sebutkan foreign key-nya secara eksplisit sebagai argumen kedua: return $this->belongsTo(User::class, 'author_id');. Kebiasaan ini juga membuat kode lebih mudah dibaca oleh developer yang baru bergabung.

Setelah didefinisikan, relasi diakses seperti properti biasa, misalnya $post->user->name. Kemudahan inilah yang membuat Eloquent nyaman dipakai, sekaligus menjadi sumber masalah yang akan kita bahas.

Bagaimana N+1 Query Terjadi

Bayangkan controller mengambil data dengan $posts = Post::latest()->take(50)->get();, lalu view menampilkan nama penulis di setiap baris lewat $post->user->name di dalam perulangan.

Query pertama mengambil 50 artikel. Karena relasi user belum dimuat, Eloquent menjalankan satu query tambahan setiap kali sebuah baris mengakses penulisnya. Totalnya 51 query: satu untuk daftar, ditambah N untuk setiap baris. Dari situlah nama N+1 berasal.

Di laptop pengembang dengan sepuluh baris data, masalah ini nyaris tak terasa. Di server produksi, halaman yang sekaligus menampilkan penulis, kategori, jumlah komentar, dan tag bisa menjalankan ratusan query untuk sekali buka, dan semuanya bertambah seiring jumlah data.

N+1 juga sering bersembunyi di tempat yang tidak langsung terlihat, misalnya accessor model, komponen Blade, atau API Resource yang mengakses relasi untuk setiap item. Kodenya tampak rapi, tetapi tetap memicu satu query per baris.

Eager Loading dengan with()

Solusinya adalah memberi tahu Eloquent sejak awal relasi apa saja yang dibutuhkan. Ubah query menjadi Post::with('user')->latest()->take(50)->get(), dan Eloquent hanya menjalankan dua query: satu untuk artikel dan satu lagi untuk semua penulisnya sekaligus, memakai klausa WHERE id IN (...).

Beberapa relasi bisa dimuat bersamaan dengan array, misalnya Post::with(['user', 'tags'])->get(). Relasi bersarang memakai tanda titik: Post::with('comments.user')->get() memuat komentar beserta penulis tiap komentar.

Jika tabel users punya banyak kolom, batasi yang diambil dengan Post::with('user:id,name')->get(). Sertakan selalu kolom id dan kolom kunci relasi yang dibutuhkan, karena tanpa itu Eloquent tidak bisa memasangkan data induk dengan relasinya.

Eager loading juga bisa diberi syarat. Untuk memuat komentar yang sudah disetujui saja, gunakan closure: Post::with(['comments' => fn ($query) => $query->where('approved', true)])->get(). Jumlah query tetap dua, tetapi data yang dibawa ke memori lebih sedikit.

load(), loadMissing(), dan withCount()

Kadang model sudah telanjur diambil, misalnya lewat route model binding. Untuk kasus seperti ini gunakan lazy eager loading: $post->load('comments.user'); memuat relasi dalam satu langkah, sedangkan loadMissing() hanya memuat relasi yang belum ada sehingga aman dipanggil berulang.

Untuk menampilkan jumlah komentar, jangan memuat semua komentar lalu menghitungnya di PHP. Pakai Post::withCount('comments')->get(); hasilnya tersedia di atribut $post->comments_count dan dihitung langsung oleh database lewat subquery.

Mencegah Lazy Loading sejak Pengembangan

Cara paling ampuh adalah membuat Laravel menolak lazy loading selama pengembangan. Tambahkan Model::preventLazyLoading(! $this->app->isProduction()); di method boot pada AppServiceProvider, dengan Model diimpor dari Illuminate\Database\Eloquent\Model.

Setelah itu, setiap relasi yang dimuat diam-diam akan memicu LazyLoadingViolationException, sehingga N+1 ketahuan saat Anda membuka halaman di laptop sendiri, bukan saat pelanggan mengeluh. Argumen di dalamnya memastikan aturan ini tidak aktif di produksi. Bila ingin tetap memantaunya di sana, catat pelanggaran ke log lewat Model::handleLazyLoadingViolationUsing().

Sejak Laravel 12.8 juga tersedia eager loading otomatis lewat Model::automaticallyEagerLoadRelationships();. Saat fitur ini aktif dan satu model dalam koleksi mengakses relasi yang belum dimuat, Laravel memuat relasi itu untuk seluruh koleksi sekaligus. Jika tidak ingin mengaktifkannya untuk semua model, panggil withRelationshipAutoloading() pada koleksi tertentu saja.

Fitur otomatis ini praktis sebagai jaring pengaman. Namun with() yang ditulis eksplisit tetap lebih mudah dipahami rekan setim, karena kebutuhan data terlihat langsung di query.

Alat untuk Mendeteksi Query Berlebih

  • Laravel Debugbar, kini dengan nama paket fruitcake/laravel-debugbar, menampilkan jumlah dan isi query di setiap halaman. Pasang hanya untuk pengembangan: composer require fruitcake/laravel-debugbar --dev.

  • Laravel Telescope mencatat setiap query beserta durasinya, cocok untuk menelusuri request yang terasa lambat.

  • Laravel Pulse menyediakan kartu Slow Queries untuk memantau query lambat di aplikasi yang sudah berjalan.

  • Tanpa paket tambahan, DB::listen(fn ($query) => logger($query->sql)); di AppServiceProvider menulis setiap query ke berkas log.

Selain jumlah query, periksa juga indeksnya. Eager loading untuk relasi hasMany menghasilkan query berbentuk WHERE post_id IN (...), sehingga kolom foreign key seperti post_id perlu diindeks. Kabar baiknya, di MySQL kolom yang dibuat dengan foreignId()->constrained() otomatis mendapat indeks karena InnoDB mewajibkannya. Pembahasan lengkapnya ada di artikel mengenal indeks di MySQL.

Kesimpulan

N+1 query adalah masalah yang tumbuh diam-diam bersama data. Beberapa kebiasaan kecil berikut sudah cukup untuk mencegahnya:

  • Setiap kali view menampilkan data relasi di dalam perulangan, muat relasinya dengan with().

  • Gunakan withCount() untuk angka dan with('relasi:kolom') untuk membatasi kolom yang diambil.

  • Aktifkan preventLazyLoading() di lingkungan pengembangan.

  • Pantau jumlah query dengan Debugbar atau Telescope sebelum fitur dirilis.

Detail setiap jenis relasi, termasuk relasi polimorfik dan has-many-through, bisa Anda pelajari di dokumentasi Eloquent Relationships.
