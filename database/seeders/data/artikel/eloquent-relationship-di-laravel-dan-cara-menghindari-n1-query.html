Halaman daftar artikel yang dulu terbuka dalam sekejap tiba-tiba terasa berat setelah datanya mencapai ratusan baris. Sering kali penyebabnya bukan server yang kurang kuat, melainkan Eloquent yang diam-diam menjalankan puluhan hingga ratusan query kecil.

Artikel ini mengulas empat relasi Eloquent yang paling umum, lalu membedah masalah N+1 query: dari mana asalnya, cara memperbaikinya dengan eager loading, dan cara mendeteksinya sebelum pengguna merasakannya.

Empat Relasi yang Paling Umum

Anda menulis relasi Eloquent sebagai method di dalam model. Laravel menebak nama kolom dari konvensi. Dengan demikian, tabel posts cukup memiliki kolom user_id agar terhubung ke tabel users tanpa konfigurasi tambahan.

  • hasOne, untuk satu baris yang memiliki tepat satu pasangan, misalnya pengguna dengan profilnya. Di model User: return $this->hasOne(Profile::class);

  • hasMany, untuk satu baris yang memiliki banyak pasangan, misalnya satu penulis dengan banyak artikel: return $this->hasMany(Post::class);

  • belongsTo, kebalikan dari keduanya, untuk model yang menyimpan foreign key. Di model Post: return $this->belongsTo(User::class);

  • belongsToMany, untuk relasi banyak ke banyak lewat tabel perantara, misalnya artikel dan tag. Laravel mengharapkan tabel post_tag, yaitu gabungan nama kedua model menurut urutan abjad: return $this->belongsToMany(Tag::class);

Bila tabel tidak mengikuti konvensi, misalnya kolom penulis bernama author_id, sebutkan foreign key-nya secara eksplisit sebagai argumen kedua: return $this->belongsTo(User::class, 'author_id');. Kebiasaan ini juga memudahkan pengembang yang baru bergabung membaca kode.

Setelah relasi terdefinisi, Anda bisa mengaksesnya seperti properti biasa, misalnya $post->user->name. Kemudahan inilah yang membuat Eloquent praktis. Namun, kemudahan yang sama juga menjadi sumber masalah yang akan kita bahas.

Bagaimana N+1 Query Terjadi

Bayangkan controller mengambil data dengan $posts = Post::latest()->take(50)->get();, lalu view menampilkan nama penulis di setiap baris lewat $post->user->name di dalam perulangan.

Query pertama mengambil 50 artikel. Setelah itu, Eloquent menjalankan satu query tambahan setiap kali sebuah baris mengakses penulisnya karena relasi user belum termuat. Totalnya 51 query, yaitu satu untuk daftar dan N untuk N baris. Dari situlah nama N+1 berasal.

Di laptop pengembang dengan sepuluh baris data, masalah ini nyaris tak terasa. Di server produksi, halaman yang sekaligus menampilkan penulis, kategori, jumlah komentar, dan tag bisa menjalankan ratusan query untuk sekali buka. Jumlah itu pun terus bertambah seiring dengan pertumbuhan data.

N+1 juga sering bersembunyi di tempat yang tidak langsung terlihat. Contohnya, N+1 muncul saat accessor model, komponen Blade, atau API Resource mengakses relasi untuk setiap item. Kodenya tampak rapi, tetapi tetap memicu satu query per baris.

Eager Loading dengan with()

Solusinya adalah memberi tahu Eloquent sejak awal relasi apa saja yang Anda perlukan. Ubah query menjadi Post::with('user')->latest()->take(50)->get(). Eloquent kini hanya menjalankan dua query: satu untuk artikel dan satu lagi untuk mengambil semua penulisnya sekaligus lewat klausa WHERE id IN (...).

Anda bisa memuat beberapa relasi bersamaan dengan array, misalnya Post::with(['user', 'tags'])->get(). Relasi bersarang memakai tanda titik: Post::with('comments.user')->get() memuat komentar beserta penulis tiap komentar.

Jika tabel users memiliki banyak kolom, batasi kolom yang Anda ambil dengan Post::with('user:id,name')->get(). Selalu sertakan kolom id dan kolom kunci relasi yang Anda perlukan. Tanpa kolom-kolom itu, Eloquent tidak bisa memasangkan data induk dengan relasinya.

Eager loading juga bisa bersyarat. Gunakan closure agar Eloquent hanya memuat komentar yang sudah mendapat persetujuan: Post::with(['comments' => fn ($query) => $query->where('approved', true)])->get(). Jumlah query tetap dua, tetapi data yang masuk ke memori lebih sedikit.

load(), loadMissing(), dan withCount()

Kadang model sudah telanjur terambil, misalnya lewat route model binding. Dalam kasus seperti ini, gunakan lazy eager loading: $post->load('comments.user'); memuat relasi dalam satu langkah. Sementara itu, loadMissing() hanya memuat relasi yang belum ada sehingga Anda aman memanggilnya berulang kali.

Saat menampilkan jumlah komentar, jangan memuat semua komentar lalu menghitungnya di PHP. Pakai Post::withCount('comments')->get(). Hasilnya tersedia di atribut $post->comments_count. Basis data menghitung angka itu langsung lewat subquery.

Mencegah Lazy Loading sejak Pengembangan

Cara paling ampuh adalah membuat Laravel menolak lazy loading selama pengembangan. Tambahkan Model::preventLazyLoading(! $this->app->isProduction()); di method boot pada AppServiceProvider. Jangan lupa mengimpor Model dari Illuminate\Database\Eloquent\Model.

Setelah itu, setiap upaya memuat relasi secara diam-diam akan memicu LazyLoadingViolationException. Dengan demikian, N+1 ketahuan saat Anda membuka halaman di laptop sendiri, bukan saat pelanggan mengeluh. Argumen di dalam preventLazyLoading() memastikan aturan ini tidak aktif di produksi. Bila Anda tetap ingin memantaunya di produksi, catat pelanggaran ke log lewat Model::handleLazyLoadingViolationUsing().

Sejak versi 12.8, Laravel juga menyediakan eager loading otomatis lewat Model::automaticallyEagerLoadRelationships();. Saat fitur ini aktif dan satu model dalam koleksi mengakses relasi yang belum termuat, Laravel memuat relasi itu untuk seluruh koleksi sekaligus. Jika Anda tidak ingin mengaktifkannya untuk semua model, panggil withRelationshipAutoloading() pada koleksi tertentu saja.

Fitur otomatis ini praktis sebagai jaring pengaman. Namun, rekan setim tetap lebih mudah memahami with() yang tertulis eksplisit karena kebutuhan datanya langsung terlihat di query.

Alat untuk Mendeteksi Query Berlebih

  • Laravel Debugbar, kini dengan nama paket fruitcake/laravel-debugbar, menampilkan jumlah dan isi query di setiap halaman. Pasang paket ini hanya untuk pengembangan: composer require fruitcake/laravel-debugbar --dev.

  • Laravel Telescope mencatat setiap query beserta durasinya sehingga cocok untuk menelusuri permintaan yang terasa lambat.

  • Laravel Pulse menyediakan kartu Slow Queries untuk memantau query lambat di aplikasi yang sudah berjalan.

  • Tanpa paket tambahan, DB::listen(fn ($query) => logger($query->sql)); di AppServiceProvider menulis setiap query ke berkas log.

Selain jumlah query, periksa juga indeksnya. Eager loading untuk relasi hasMany menghasilkan query berbentuk WHERE post_id IN (...). Oleh karena itu, kolom foreign key seperti post_id memerlukan indeks. Kabar baiknya, di MySQL, kolom hasil foreignId()->constrained() otomatis mendapat indeks karena InnoDB mewajibkannya. Pembahasan lengkapnya ada di artikel mengenal indeks di MySQL.

Kesimpulan

N+1 query adalah masalah yang tumbuh diam-diam bersama data. Beberapa kebiasaan kecil berikut sudah cukup untuk mencegahnya:

  • Setiap kali view menampilkan data relasi di dalam perulangan, muat relasinya dengan with().

  • Gunakan withCount() untuk angka dan with('relasi:kolom') untuk membatasi kolom yang Anda ambil.

  • Aktifkan preventLazyLoading() di lingkungan pengembangan.

  • Pantau jumlah query dengan Debugbar atau Telescope sebelum merilis fitur.

Detail setiap jenis relasi, termasuk relasi polimorfik dan has-many-through, bisa Anda pelajari di dokumentasi Eloquent Relationships.
