Aplikasi kasir yang lancar di bulan pertama sering mulai tersendat setelah tabel transaksinya berisi ratusan ribu baris. Kodenya tidak berubah dan servernya sama, tetapi laporan harian yang dulu muncul seketika kini membuat pengguna menunggu.

Penyebab yang paling umum adalah query yang terpaksa membaca seluruh tabel karena tidak ada indeks yang sesuai. Artikel ini menjelaskan cara kerja indeks di MySQL, kolom mana yang layak mendapat indeks, cara memeriksa query dengan EXPLAIN, dan kesalahan penulisan query yang membuat MySQL mengabaikan indeks.

Cara Kerja Indeks, Mirip Indeks di Belakang Buku

Bayangkan Anda mencari kata normalisasi di buku basis data setebal 500 halaman. Tanpa daftar indeks di bagian belakang buku, Anda harus membalik halaman satu per satu. Dengan indeks, Anda langsung tahu kata itu ada di halaman berapa saja.

Indeks di MySQL bekerja dengan prinsip yang sama. Sebagian besar indeks, termasuk PRIMARY KEY, UNIQUE, dan INDEX biasa, memakai struktur B-tree. Nilai di dalam struktur ini tersusun urut dan bercabang sehingga MySQL cukup menelusuri beberapa tingkat untuk menemukan baris yang cocok, alih-alih memeriksa jutaan baris.

Di InnoDB, mesin penyimpanan bawaan MySQL, data tabel sendiri tersusun menurut primary key. Indeks lain menyimpan nilai primary key sebagai penunjuk ke baris aslinya. Oleh karena itu, primary key sebaiknya ringkas, misalnya bilangan bulat yang bertambah otomatis.

Kolom yang Layak Mendapat Indeks

Indeks paling berguna pada kolom yang sering muncul di tiga tempat berikut:

  • Klausa WHERE, misalnya pencarian pesanan berdasarkan status atau nomor faktur.

  • Kolom penghubung pada JOIN, terutama foreign key seperti id_pelanggan di tabel pesanan. InnoDB otomatis membuat indeks untuk kolom yang memiliki constraint FOREIGN KEY bila indeksnya belum ada.

  • Klausa ORDER BY dan GROUP BY. MySQL bisa membaca data yang sudah urut di indeks tanpa proses pengurutan tambahan.

Perhatikan juga selektivitasnya. Kolom dengan banyak nilai berbeda, seperti email atau nomor faktur, sangat cocok mendapat indeks. Indeks pada kolom yang nilainya hanya dua atau tiga macam jarang membantu bila berdiri sendiri. Query-nya tetap harus membaca sebagian besar tabel. Dalam kasus seperti itu, MySQL sering memilih membaca seluruh tabel secara berurutan karena cara ini justru lebih cepat.

Membuat indeks cukup dengan satu perintah: CREATE INDEX idx_pesanan_status ON pesanan (status);

Indeks Gabungan dan Aturan Prefiks Paling Kiri

Satu indeks bisa mencakup beberapa kolom sekaligus, paling banyak 16 kolom. Misalnya, laporan kasir sering menyaring pesanan berdasarkan status, lalu mengurutkannya menurut tanggal pesanan: CREATE INDEX idx_status_tanggal ON pesanan (status, tanggal_pesan);

Urutan kolom di indeks gabungan sangat menentukan. MySQL hanya bisa memakai indeks itu untuk mencari baris bila query menyertakan kolom dari sisi paling kiri. Berikut contohnya pada indeks di atas:

  • WHERE status = 'lunas' memakai indeks.

  • WHERE status = 'lunas' AND tanggal_pesan >= '2026-08-01' memakai kedua kolom indeks.

  • WHERE tanggal_pesan >= '2026-08-01' saja tidak bisa memakai indeks itu untuk mencari baris karena kondisi ini tidak menyertakan kolom status yang berada di depannya.

Aturan praktisnya: letakkan kolom yang Anda bandingkan dengan tanda sama dengan di depan, lalu kolom rentang atau pengurutan di belakang. MySQL 8.0.13 ke atas memang memiliki pengoptimalan skip scan yang kadang bisa melompati kolom pertama, tetapi syaratnya sempit. Oleh karena itu, jangan menjadikannya andalan saat merancang indeks.

Membaca Hasil EXPLAIN

Jangan menebak apakah sebuah query memakai indeks. Tambahkan EXPLAIN di depannya, misalnya EXPLAIN SELECT * FROM pesanan WHERE status = 'lunas' ORDER BY tanggal_pesan DESC;, lalu perhatikan beberapa kolom hasilnya:

  • type: nilai ALL berarti MySQL membaca seluruh tabel. Nilai seperti const, eq_ref, ref, dan range menandakan bahwa MySQL memakai indeks untuk mencari baris.

  • key: nama indeks yang benar-benar terpakai. Bila isinya NULL, MySQL tidak memakai indeks apa pun.

  • rows: perkiraan jumlah baris yang harus diperiksa. Makin kecil, makin baik.

  • Extra: waspadai Using filesort dan Using temporary. Keduanya menandakan bahwa MySQL membutuhkan kerja tambahan untuk mengurutkan atau mengelompokkan data.

MySQL 8.0.18 ke atas menyediakan EXPLAIN ANALYZE untuk angka yang lebih nyata. Perintah ini benar-benar menjalankan query, lalu melaporkan waktu dan jumlah baris aktualnya. Oleh karena itu, hindari memakainya untuk query berat di server produksi saat jam sibuk. Anda bisa membaca penjelasan setiap kolom di dokumentasi resmi EXPLAIN.

Kesalahan yang Membuat Indeks Tidak Terpakai

MySQL bisa saja mengabaikan indeks yang sudah ada karena cara Anda menulis query. Kesalahan pertama adalah membungkus kolom dengan fungsi. Query WHERE YEAR(tanggal_pesan) = 2026 memaksa MySQL menghitung YEAR() untuk setiap baris sehingga indeks pada tanggal_pesan tidak bisa membantu pencarian.

Tulis ulang kondisinya sebagai rentang: WHERE tanggal_pesan >= '2026-01-01' AND tanggal_pesan < '2027-01-01'. Bila Anda memang tidak bisa menghindari fungsi, MySQL 8.0.13 ke atas mendukung indeks fungsional seperti CREATE INDEX idx_tahun ON pesanan ((YEAR(tanggal_pesan)));. Perhatikan tanda kurung gandanya karena ekspresi dalam definisi indeks wajib memakai tanda kurung sendiri.

Kesalahan kedua adalah LIKE dengan wildcard di depan. Pencarian WHERE nama LIKE 'budi%' masih bisa memakai indeks karena awal katanya sudah pasti. Sebaliknya, LIKE '%budi' atau '%budi%' membuat MySQL memeriksa semua baris. Pertimbangkan indeks FULLTEXT dengan MATCH ... AGAINST untuk mencari kata di dalam teks panjang seperti deskripsi produk.

Kesalahan ketiga lebih halus: membandingkan kolom dengan tipe data berbeda. Bila Anda membandingkan kolom nomor_hp yang bertipe teks dengan angka tanpa tanda kutip, MySQL terpaksa mengonversi nilai di setiap baris sehingga indeksnya tidak terpakai untuk pencarian.

Indeks Juga Ada Biayanya

Indeks bukan makan siang gratis. Setiap INSERT, UPDATE, dan DELETE harus ikut memperbarui semua indeks di tabel tersebut. Selain itu, setiap indeks memakan ruang disk serta memori. Tabel log yang terus menerima data baru bisa melambat bila memiliki terlalu banyak indeks yang jarang terpakai.

Sebelum menghapus indeks yang tampak tidak berguna, uji dulu dengan menjadikannya tak terlihat: ALTER TABLE pesanan ALTER INDEX idx_pesanan_status INVISIBLE;. Optimizer akan mengabaikannya, tetapi MySQL tetap memperbarui indeks tersebut. Anda bisa mengaktifkannya kembali seketika dengan VISIBLE. View sys.schema_unused_indexes juga membantu Anda menemukan indeks yang tidak pernah terpakai sejak server terakhir kali menyala.

Rencanakan juga penambahan indeks pada tabel besar di server produksi. Lakukan di luar jam sibuk dan pastikan ada cadangan terbaru sebelum mengubah struktur tabel. Panduan membuat cadangan ada di artikel pencadangan basis data MySQL otomatis.

Rangkuman

Indeks yang tepat sering membuat query yang tadinya lambat kembali terasa instan, tanpa perlu mengganti server. Kuncinya adalah mengikuti pola query yang sebenarnya, bukan menambahkan indeks di semua kolom.

Mulailah dari query yang paling sering berjalan atau paling lambat, periksa dengan EXPLAIN, lalu tambahkan indeks yang sesuai dengan pola WHERE, JOIN, dan ORDER BY-nya. Ulangi pemeriksaan setelah Anda membuat indeks untuk memastikan hasilnya. Rawat juga indeks seperti Anda merawat kode: hapus yang tidak lagi terpakai.
